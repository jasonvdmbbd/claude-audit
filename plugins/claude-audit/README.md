# Claude Code audit log

A durable, queryable record of every prompt turn in every Claude Code session
on this machine — because the transcripts Claude Code keeps for itself
(`~/.claude/projects/**/*.jsonl`) are internal, undocumented, and auto-cleaned
after roughly 30 days.

Four files:

- **`audit_log.py`** — stdlib-only Python script, wired in as three Claude
  Code hooks, plus a `sync` subcommand that backfills the database from
  transcripts the hooks never saw, and a `merge` subcommand that folds a
  backed-up database back into a live one. Mirrors completed turns into
  SQLite and tags them out-of-band. It also carries a watchdog that keeps
  `service.py` running behind every finished turn (see The service, below).
- **`service.py`** — a stdlib-only, loopback-only local HTTP service
  (`http://127.0.0.1:4737/` by default) that puts the viewer behind a real
  origin instead of `file://`: it hands out a consistent snapshot of the
  database, pushes a refresh the moment it changes, and serves the raw bytes
  of a file a turn touched so `fileview.html` can render it. Almost every
  route is read-only; the one deliberate exception is `POST /api/merge`,
  which folds a separately backed-up database into the live one for the
  machine-rebuild case, driving the same merge engine the CLI's `merge`
  subcommand does (see `/api/merge` and Merge database UI, below).
- **`viewer.html`** — the viewer page. Opened directly (`file://`, or
  double-clicked) it's the original standalone experience: pick or drag a
  `.db` file and everything renders client-side, no server, no build step.
  Opened through `service.py` it auto-loads the live database instead and
  stays in sync (see Service mode, under Viewer usage, below).
- **`fileview.html`** — the artifact renderer behind a "Files touched" link
  in the viewer's turn detail. Only reachable through `service.py`
  (`/view?path=...`); there is nothing for it to render from a bare
  `file://` page.

## What it does

On every prompt turn, in every workspace where the hooks are installed:

1. The turn's prompt, response text, token usage, and every tool call it made
   are extracted from that session's JSONL transcript and written into **one
   database for the whole machine**, at `~/.claude/audit/audit.db` by
   default — every workspace's turns land in the same file, told apart by
   the `sessions.workspace` column. Override the location with the
   `CLAUDE_AUDIT_DB` environment variable or an explicit `--db PATH` on a
   subcommand; a per-workspace database (the old default, one file per
   project) is still available, it is just opt-in now — point `--db` at
   `<workspace>/.claude/audit/audit.db` (or set `CLAUDE_AUDIT_DB` before
   installing the hooks in that workspace) to get it back.
2. Every subagent the turn spawned — a Task agent or a workflow step alike —
   is mirrored the same way from its own sidecar transcript into a separate
   `agents` table and joined back to the parent turn, so "what did this turn
   actually do" includes the work it delegated, not just what it did itself.
3. The turn is tagged and titled. Genuine human prompts get exactly one tag
   from a fixed seven-entry taxonomy, plus a short one-sentence **title**
   (e.g. "Added retry logic to the upload handler") — generated by a detached
   call to Haiku, with a deterministic keyword/permission-mode heuristic as a
   fallback if the model call fails or is disabled:

   | Tag | Meaning |
   |---|---|
   | `plan` | exploring, researching, designing, deciding an approach |
   | `build` | writing or changing product code/features |
   | `fix` | debugging and repairing something broken |
   | `validate` | testing, reviewing, verifying behavior |
   | `docs` | writing documentation, READMEs, runbooks |
   | `ops` | environment/tooling work: installs, hooks, config, CI, deploys |
   | `chat` | conversational Q&A with no work product |

   This is the single source of truth (`TAG_TAXONOMY` in `audit_log.py`): it
   renders the Haiku classifier's own rubric and validates the model's answer
   against it, so adding or renaming a tag is a one-place edit. The `tag`
   column itself is deliberately **not** a SQL `CHECK` constraint — an older
   release constrained it (first to three tags, later to those plus
   `system:%`), but SQLite cannot alter a `CHECK` in place, so every taxonomy
   change meant a full table rebuild. The vocabulary is enforced in code
   instead, and `sync` rebuilds any older database still carrying one of
   those constraints (see `relax_tag_check`) the first time it opens it, so
   the widening happens automatically — no manual migration step.
   Machine-generated prompts are flagged `is_synthetic` and get a
   deterministic **`system:*` kind** instead (no model call — the text says
   exactly what machinery produced it):

   | Kind | Meaning | Title pattern |
   |---|---|---|
   | `system:command` | Slash-command expansion | "Slash command: /name" |
   | `system:interrupt` | User interrupted the previous turn | "Turn interrupted by user" |
   | `system:task-result` | Background task/agent/workflow notification | The notification's own summary |
   | `system:context` | Harness-injected context (system reminders etc.) | "Harness-injected context" |

   The human tag ratios therefore stay pure: machinery never contributes to
   them. `sync` re-marks legacy rows to this scheme idempotently (the tag
   `CHECK` constraint, on a database old enough to still have one, is
   widened away by the automatic table rebuild described above on first
   open).

   A turn's tag can also be *reopened*: if its response text is longer or
   different the next time that turn is written (typically `Stop` firing
   against a reply that was still streaming its final blocks), the row's
   `tag`/`title`/`tag_source` are dropped right there, so the next classifier
   pass — the `Stop` hook's own fire-and-forget call, or a later
   `sync --classify` — retags it from the complete text instead of leaving it
   wearing a title that describes only half of it. Synthetic turns are exempt,
   since their kind is derived from the prompt, which never changes.

   **The tagging hierarchy runs four levels deep, only two of them ever
   touching a model:**

   | What | Tagged by | Taxonomy | Where |
   |---|---|---|---|
   | A human turn | Haiku, heuristic fallback | `TAG_TAXONOMY` (the 7 tags above) | `turns.tag`/`title`/`tag_source` |
   | A subagent | Haiku, heuristic fallback — same rubric | `TAG_TAXONOMY`, identical | `agents.tag`/`title`/`tag_source` |
   | An ordinary tool call | Deterministic name/input mapping, plus a template one-line summary | `TAG_TAXONOMY`, no `system:*` | `tool_calls`/`agent_tool_calls`.`tag`/`summary` |
   | A task-spawning call (`Agent`/`Workflow`/`Task`) | Deterministic, from its own spawn description | `TAG_TAXONOMY` | same two columns, via `tool_tag()`'s spawn branch |

   A subagent is classified exactly like a turn — `classify_agent` hands the
   model the agent's own spawning prompt and its final result in place of a
   turn's prompt/response, so the same rubric, the same `VALID_TAGS`
   validation, the same title rule and the same `CLAUDE_AUDIT_NO_LLM` opt-out
   apply, and an agent's tag is directly comparable with a turn's (see
   `--classify`, below, and Subagents, below). A tool call is never put to a
   model at all: `tool_tag_and_summary()` is a pure function of the call's
   `tool_name` and its (possibly truncated) stored `input_json`, so tagging
   never depends on what the call *returned*, converges the same way whether
   it runs at capture time or in a backfill years later, and never blocks a
   turn on an LLM round trip for something a name and an input already answer
   (see Tool-call and task-spawn tagging, below).
4. Every turn also records where it sits in the conversation: the transcript
   line's own `parentUuid` and `uuid` are kept as `parent_uuid`/`last_uuid`,
   turning `turns` into a graph rather than a flat list — a rewind, an edited
   prompt, or a `/resume` all show up as a **fork** (two turns sharing the
   same `parent_uuid`) instead of silently overwriting history.
5. A backgrounded `Bash` command, a background `Agent` spawn, and a
   `Workflow` run each answer their spawning tool call with an id, and the
   harness later delivers a synthetic `<task-notification>` prompt carrying
   that same id once the work finishes. Both ends of that loop are recorded —
   `tool_calls.task_id`/`run_ref` on the call that started it,
   `turns.task_id` on the `system:task-result` turn that reported it done —
   so "what did this spawn, and what came back" is answerable straight from
   the database, long after the background task itself has finished and the
   live agents/workflow state that produced it is gone (see Background
   tasks, below).
6. `viewer.html` opens that `.db` file (via drag-and-drop or a file picker)
   entirely client-side and renders a filterable, searchable list of turns —
   totals, per-tag counts, sessions, and each turn's prompt/response/tool
   calls (and any agents it spawned) in a detail panel. A "Hide system turns"
   toggle (on by default) filters out the `is_synthetic` rows, and a
   **workspace** dropdown narrows everything to one folder when a database
   tracks more than one. A **Flow** view sits alongside the list: a node-based
   diagram of the same session's turns, tool calls, agents and their tool
   calls, click-to-expand, with a background task's spawn drawn as its own
   marked node and edge. A **Dashboard** view sits alongside both: aggregate
   sections (headline totals, activity over time, cost by workspace/tag,
   the most expensive turns, sub-agent delegation, efficiency ratios) priced
   by one embedded, provider-aware rate table shared with every per-row cost
   figure in the other two views (see Pricing, and Viewer usage / Dashboard
   view, below). Opened through `service.py` instead, the same page
   auto-loads the live database with no file picking at all, and a turn's
   Files-touched panel links straight to the file itself, previewed inline
   (see The service, and Viewer usage / Service mode, below).
7. A one-off `sync` run (or the `/audit-sync` slash command) backfills the
   database from every transcript already on disk, for workspaces that
   predate the hooks or missed turns the hooks never saw. Since the audit is
   machine-wide, `sync` with no flags means **every** workspace it can find
   under `~/.claude/projects` (this is `--all`, and it's the default); pass
   `--workspace PATH` to narrow a run to one project instead. A `merge` run
   folds a separately backed-up database back into the live one, for the
   corporate restore case where a machine was wiped and rebuilt (see Merge,
   below).

The goal: nothing a Claude Code session does should exist only in a
transcript that can quietly disappear. If it happened, it's in the DB.

## How it works

### Hooks

`audit_log.py` is dispatched by `hook_event_name` on stdin and handles three
events:

| Hook | What it does |
|---|---|
| `UserPromptSubmit` | Fast path only: inserts a `pending` row for the new turn (session id, prompt text, permission mode, timestamp). No transcript read, no LLM call — keeps prompt submission unblocked. |
| `Stop` | Sweeps the transcript from the session's saved byte offset, assembles every newly-completed turn, persists it (`status = 'complete'`), and fire-and-forgets a Haiku classifier subprocess per newly completed turn. |
| `SessionEnd` | Re-sweeps the transcript (catches anything `Stop` never saw — see Caveats), marks any turns it finalizes as `status = 'swept'`, updates the session's `ended_at`/`end_reason`, recovers classification for any turn that never got tagged, and archives a verbatim copy of the raw transcript. |

**Transcript extraction** is cursor-based: each session's byte offset into
its own JSONL transcript is stored in the `cursors` table, so every sweep
only reads what's new. Turns are re-persisted idempotently (matched first by
`prompt_uuid`, then by pending `prompt_id`, then the oldest unclaimed
pending row), so re-sweeping the same lines on `SessionEnd` is safe and
never duplicates a turn. Only top-level `user`/`assistant` lines are
consumed — lines with `isSidechain` (subagent traffic) or `isMeta` are
skipped. `persist_turns` deliberately rewinds the cursor to the *start* of
the last turn it saw rather than to EOF, because tool-result blocks can still
land on that turn after `Stop` fires — re-reading it next sweep is cheap and
harmless, since persistence is idempotent either way.

**Reclassify on growth**: that same rewind is what makes a turn's response
visibly *grow* between sweeps, and `persist_turn` treats a growing or changed
response on an already-tagged row as a sign it was tagged from an incomplete
turn — commonly `Stop` firing while the assistant's final text blocks were
still being written. When that happens it drops the row's `tag`, `title` and
`tag_source` back to `NULL` in the same update, which both re-opens it for
the classifier (the `Stop` handler's own fire-and-forget call, `sync
--classify`'s `tag IS NULL` query, and `SessionEnd`'s untagged-turn recovery
all pick it up the same way a brand-new turn would) and surfaces it in a
sync's summary as a `reclassified` count ("re-opened: N turn(s) whose
response grew since tagging"). A synthetic turn is never reclassified this
way — its kind comes from the prompt text, not the response, so a growing
response can't stale it.

**Classification** runs out-of-band so it never blocks the turn:
`spawn_classifier()` launches a detached `python3 audit_log.py classify
--db ... --turn ...` subprocess (`start_new_session=True`, so it survives
the hook process exiting). That subprocess shells out to:

```
claude -p --model claude-haiku-4-5-20251001 --output-format json
```

feeding it the turn's (truncated) prompt and response and asking for strict
JSON `{"tag": "...", "title": "..."}`. It runs in a single fixed scratch
directory (`$TMPDIR/claude-audit-classifier`) rather than the audited
workspace, so classifier runs don't pollute the workspace's own transcript
project directory or create a new junk directory per turn.

**Recursion guard**: the classifier's own `claude -p` call would itself fire
these same hooks. It's launched with `CLAUDE_AUDIT_SKIP=1` in its
environment, and `audit_log.py`'s hook entry point exits immediately (before
reading stdin) whenever that variable is set — so a classifier session can
never recursively log or re-classify itself. Explicit subcommands
(`classify`, `init`, `sync`) are exempt from this check, since the classifier
subprocess must always be able to run `classify` regardless of the guard it
sets for its *own* inner session.

**Turn lineage**: Claude Code's transcript is itself a linked list — every
line carries its own `uuid` and the `parentUuid` of the line it answers.
`new_turn`/`chain_tip` keep two of those per turn: `parent_uuid` (the prompt
line's own `parentUuid`) and `last_uuid` (the `uuid` of the turn's last
main-thread line — the one anything answering *this* turn will name as its
`parentUuid`). Together they turn `turns` from a flat, session-ordered list
into a graph:

* turn B is a **child** of turn A when `B.parent_uuid == A.last_uuid`;
* two turns sharing the same `parent_uuid` are a **fork** — the same point in
  the conversation was continued twice (a rewind, an edited-and-resubmitted
  prompt, a `/resume` that branches off an earlier point);
* a turn whose `parent_uuid` is `NULL`, or matches no `last_uuid` anywhere in
  the session, is a **root** of its own branch.

Subagents join this same graph a different way, through `agents.turn_id` /
`agents.prompt_id`, so turn-to-turn lineage plus turn-to-agent spawns
together describe the whole tree — which is exactly what the viewer's Flow
view draws (see Viewer usage, below).

**Relinked backfill**: `parent_uuid`/`last_uuid` are columns added after the
first release, so rows written before then (and any row the live hooks
opened but whose closing transcript line they never saw) carry `NULL`
lineage. `sync` closes that gap with `relink_turns`: whenever a session has
any turn missing its `last_uuid`, the transcript is re-read once, purely in
memory, to rebuild the `parent_uuid`/`last_uuid` pair for every turn in it
(`session_lineage` — a deliberately minimal re-walk that mirrors
`assemble_turns`' own grouping rules but keeps nothing except the two uuids,
so even a huge transcript costs one pass and a few kilobytes). Rows are
matched by `prompt_uuid`, which is unique, and only those two columns are
touched — the cursor table is never read or written by a relink, so it can
never disturb the incremental sync, the tags, or the token counts. A sync
run reports how many rows this touched as `relinked: N turn(s) given lineage
uuids`.

**Test/offline mode**: setting `CLAUDE_AUDIT_NO_LLM=1` skips the Haiku call
entirely and always falls through to the deterministic heuristic classifier
(`permission_mode == "plan"` → `plan`; else a keyword match against
`test/verify/validate/review/lint/assert` → `validate`; otherwise `build`;
title is the first sentence of the prompt).

Every code path swallows exceptions and appends to `hook-errors.log` next to
the database it was writing to — `~/.claude/audit/hook-errors.log` by
default, or beside whatever `--db`/`CLAUDE_AUDIT_DB` points at — a hook must
never fail the turn it's instrumenting, and hook mode never writes to stdout
(the harness parses that stream).

### Tool-call and task-spawn tagging

Every tool call — a turn's own (`tool_calls`) and a subagent's
(`agent_tool_calls`) alike — carries a `tag` from the same seven-entry
`TAG_TAXONOMY` a turn does, plus a `summary`: a one-line, human-written-style
sentence saying what the call did. **No model is ever involved.** A tool call
already says in its own name and input what kind of work it is, so
`tool_tag_and_summary(tool_name, input_json)` is a pure function of those two
values, computed once at capture time (`record_tool_use`, from the input
exactly as stored — truncation and all) and never revisited unless the row
predates the columns:

- **`AskUserQuestion`** is always `chat`.
- **`Edit`/`Write`/`MultiEdit`/`NotebookEdit`** are `docs` when the path they
  touch ends in `.md`/`.markdown`, `build` otherwise.
- **`Read`/`Grep`/`Glob`/`WebFetch`/`WebSearch`/`NotebookRead`/`LS`/`ListDir`**
  are always `plan` — looking at something, not changing it.
- **`Bash`** is read off its own command line (falling back to nothing when
  neither matches): `test`/`pytest`/`lint`/`--check`/`validate`/`verify` →
  `validate`; `install`/`deploy`/`launchctl`/`systemctl`/`config`/`chmod`/
  `mkdir`/`plugin`/`git`/`curl` → `ops`; `grep`/`find`/`ls`/`cat`/`head`/
  `tail`/`wc`/`lsof` → `plan`; matched at a word start so `ls` never fires
  inside `tools/` and `cat` never fires inside `concatenate`, though a
  trailing suffix still counts (`installing`, `tests`). Anything unmatched
  defaults to `build`.
- **Everything else** — MCP tools, harness tools, whatever ships next — is
  `ops`: tooling acting on the environment rather than the product.
- **A task-spawning call — `Agent`, `Workflow`, or `Task`** — is tagged from
  its *own spawn description*, the prose the caller wrote for it, not from a
  model: a pared-down copy of the turn heuristic's keyword groups
  (`fix`/`bug`/`error` → `fix`; `test`/`verify`/`review` → `validate`;
  `research`/`explore`/`investigate`/the verb *read* → `plan`;
  `document`/`readme` → `docs`; `install`/`setup`/`deploy` → `ops`, checked in
  that order) reads the description and falls back to `build` when nothing
  matches. This is the same mechanism a `Bash` call's command line gets, just
  aimed at prose instead of a shell invocation, which is why the taxonomy and
  the columns line up with an ordinary tool call's rather than needing a
  scheme of their own.

The **summary** half is a small template per tool family, not free text: a
file-touching call says `Read`/`Edited`/`Wrote <basename>`; `Grep`/`Glob` says
`Searched for '<pattern>'`; `WebFetch` says `Fetched <host>`; `WebSearch` says
`Searched web for '<query>'`; `Agent`/`Task`/`Workflow` echo their own spawn
description (`Agent: …` / `Workflow: …`); `AskUserQuestion` echoes the
question asked; `Bash` prefers its own `description` field over a truncated
copy of the command line; anything else, or any input that fails to parse at
all, falls back to `Called <tool name>` — so a row missing or too mangled to
read still gets a tag and a sentence rather than being left for every future
sync to re-examine. This is what shows up as the tag chip and headline in the
list view's tool-call trace and as the tinted, labelled node in Flow (see
Viewer usage, below).

Because the mapping is deterministic, a row written before these columns
existed converges the same way capture would have: `sync`'s
`backfill_tool_tags()` walks both `tool_calls` and `agent_tool_calls` in
batches of 500, tagging every row still `tag IS NULL`, and runs on **every**
sync regardless of `--classify` — there is no cost to keeping it complete,
since no model call is involved (see Sync, below).

### Subagents

A session transcript at `<projects>/<slug>/<session_id>.jsonl` has a sibling
*directory*, `<projects>/<slug>/<session_id>/subagents/`, holding one JSONL
per subagent the session spawned, in the same line format as the main
transcript but flagged `isSidechain`. `sweep_agents()` walks that tree —
directly-spawned (`Task`) agents sit at its top level next to a
`<name>.meta.json` sidecar; workflow steps sit under `workflows/<run_id>/`
instead, and that run directory becomes the row's `workflow_id`. It's called
at the end of both the `Stop` and `SessionEnd` handlers, after that turn's own
extraction, so an agent spawned by the turn that just ended always finds its
parent row already written.

**Turn linkage**: every line of an agent's file carries the *parent turn's*
`promptId`, the same join key `turns.prompt_id` carries. Each agent row is
matched to that turn (`lookup_turn_id`) as it's stored, and a
DB-wide `resolve_agent_turns()` pass afterwards backfills any agent whose
parent turn wasn't in the database yet at scan time — an agent can be written
before the turn that spawned it is finalised, and a `sync` may meet the two
files in either order, so this retry runs after every scan regardless.

**What's captured vs. what isn't**: an agent row stores its spawning prompt
(the file's first `user` line), its final result (the text of its last
assistant turn, or its `StructuredOutput` tool call's input, serialised, for
an agent given a structured-output schema), model, timestamps/duration, the
same five token columns as `turns`, and `tool_call_count` — a *count* of the
tool calls it made. Its individual tool calls (inputs and results) are
mirrored too, into `agent_tool_calls` (see below) — so a subagent's own flow
is queryable and drawable the same way a turn's is, not just countable. What
still isn't captured is the agent's own thinking/text blocks beyond its final
result: only the last assistant turn's text (or a `StructuredOutput` payload)
is kept, so the reasoning in between exists solely in the raw archived
subagent transcript (see Archive, below) — the DB row is a summary of what an
agent *did* and *concluded*, not a full replay of everything it said.

**Classification**: a subagent is tagged and titled exactly as a turn is —
`agents.tag`/`title`/`tag_source`, the same `TAG_TAXONOMY`, the same Haiku
rubric, the same heuristic fallback (see the tagging hierarchy under What it
does, and `--classify` under Sync, below) — via `classify_agent`, which puts
the model the agent's own spawning prompt (or its `description`, when the
prompt is empty, as a workflow step's can be) as the prompt and its stored
`result` as the response. This runs live, not only in a backfill:
`handle_stop` and `handle_session_end` fire a detached
`spawn_agent_classifier` subprocess per agent just scanned or still untagged
(`scan_agents` → `agent_needs_tag`), the identical fire-and-forget pattern a
turn's classifier uses, so an agent gets its tag within moments of being
mirrored, not only at the next `sync`. `carry_classification()` is the
agent-side equivalent of a turn's reclassify-on-growth: `store_agent()`
consults it on every (re)parse, and an existing `tag`/`title`/`tag_source`
survives only when the re-parsed `prompt` and `result` are byte-identical to
what the row already held — any change (or a row never classified at all)
drops back to `NULL` and lets the classifier pick it up again.

**`agent_tool_calls`** — one row per tool invocation inside an agent's own
transcript, the subagent-side counterpart to a turn's `tool_calls`. Extracted
by the same `record_tool_use`/`attach_tool_result` machinery `parse_agent_file`
reuses from turn assembly, so it carries the identical shape and truncation
limits (`input_json`/`result_text` capped at 10,000 chars, `input_truncated`/
`result_truncated` flagging it) — an agent's tool trace reads exactly like a
turn's. Rows are keyed by `(session_id, agent_id)` — the `agents` primary key
— rather than by an id of their own, and `store_agent()` rebuilds them
wholesale (`write_agent_tool_calls`: delete then re-insert in `seq` order)
every time that agent file is (re)parsed, exactly like `tool_calls` under a
turn.

**Backfill trigger**: `agent_tool_calls` shipped after `agents` already had
live data in it, so an agent row logged before the table existed would
otherwise never gain one — `store_agent()`'s own append-only/`src_bytes`
short-circuit (see Incremental rescan, below) would keep skipping it forever
since its source file never changed size. `needs_tool_backfill()` closes that
gap: whenever an unchanged-size agent's own `tool_call_count` is greater than
zero but it has no `agent_tool_calls` rows yet, it's re-parsed once purely to
populate them (reported as `backfilled` rather than `unchanged` in a sync's
per-workspace `agents:` line, e.g. "N tool-backfilled"). After that one pass
it has rows and is skipped normally on every later scan. Until a database has
been through this — before its first `sync`/`/audit-sync` since upgrading, or
for an agent the live hooks logged under an older release — an agent's modal
in the viewer falls back to reporting its `tool_call_count` with a note to run
`/audit-sync` (see Viewer usage, below) instead of showing the calls
themselves.

**Incremental rescan**: `store_agent()` compares an agent file's byte size
(`src_bytes`) against what's already stored and skips reparsing it when
unchanged — a finished agent transcript is append-only and never grows, so an
unchanged size means unchanged content (except for the one-time tool-call
backfill above).

**Archive**: alongside the raw transcript copy, `SessionEnd` (and `sync`)
also copies the whole `subagents/` tree verbatim to
`<audit dir>/transcripts/<name>-subagents/` (`<audit dir>` is wherever the
database lives — `~/.claude/audit` by default), preserving its relative
layout — including the `workflows/<run>/` structure, each agent's
`.meta.json` sidecar, and any workflow run's `journal.jsonl` — so the detail
that never makes it into the database at all (an agent's own thinking/text
blocks beyond its final result — see What's captured vs. what isn't, above)
survives Claude Code's own transcript cleanup too, as ground truth. Because one
archive directory can hold sessions from every workspace on the machine,
`<name>` is always the workspace-prefixed `archive_basename` —
`<workspace-folder>-<session_id>` — rather than the bare session id, even
for a per-workspace database, so a name never has to change meaning later if
that database is ever pointed at more than one workspace. An existing
archived copy that's
already at least as long as the source is left alone, so re-running `sync`
doesn't recopy anything unchanged.

### Background tasks

A `Bash` command run with `run_in_background`, a background `Agent` spawn, and
a `Workflow` run all share a shape worth recording on top of the ordinary
tool-call/agent-row mirroring above: the spawning tool call returns
immediately with an id, the work continues after that call's turn is already
finished, and completion arrives later as its own thing — a
`<task-notification>` prompt the harness injects as a brand-new turn. Nothing
about the ordinary extraction connects those two turns to each other; this is
the machinery that does.

**The two ends of the loop**:

* `tool_calls.task_id` — set on the row for the spawning call itself, the
  moment it's persisted — is where the background task was **started**.
* `turns.task_id` — set on the synthetic turn born from the
  `<task-notification>` prompt — is the turn that reported it **finished**.
  The same id in both places is what makes `tool_calls.task_id ==
  turns.task_id` a join between "I kicked this off" and "here's what came
  back", even though the two rows can be minutes apart and belong to
  completely different turns.
* `tool_calls.run_ref` is a *second*, independent reference parsed off the
  same spawning call's result — a workflow's `Run ID: wf_...` or an `agentId`
  hex — kept apart from `task_id` because it answers a different question:
  not "which notification closes this call" but "which mirrored rows in
  `agents` (`agents.workflow_id` or `agents.agent_id`) belong to it". A
  `Workflow` spawn's result carries both a task id and a run ref; a
  backgrounded `Bash` command carries only a task id, since there's no agent
  row on the other end of it.

**Extraction, narrowly scoped on purpose**: only `Bash`, `Agent` and
`Workflow` results are ever parsed for an id (`TASK_LINK_TOOLS`) — a `Read`
call whose file happens to contain the words "task_id: 7" must never be
mistaken for a spawn, so every other tool's result is left alone regardless
of what it contains. The id patterns themselves (`TASK_ID_PATTERNS`) cover
every wording the harness has used for it in stored transcripts — "Task ID:
x", "task_id: x", "Command running in background with ID: x", and an
`agentId` hex — and `RUN_REF_PATTERNS` similarly covers a labelled
`run id: wf_...`, the bare `wf_<hex>-...` form actually seen when a `Workflow`
result only names its run inside the transcript path it reports, and the
`agentId` hex again. On the notification side, `prompt_task_id()` reads the
`<task-id>` a harness-injected `<task-notification>` prompt carries; it's
also what titles that turn as `system:task-result`, with the notification's
own summary as the title (see What it does, above).

**Sync backfill pass**: both links are recovered from text the mirror has
*already captured* — a spawning call's stored (and possibly truncated)
result, a notification turn's stored prompt — so `backfill_task_links()`
needs no transcript re-read at all, only a scan of rows already in the
database. It's one of the whole-database passes `finalize_db` runs once per
`sync` invocation (see `--classify`, below), after the synthetic re-marking
pass so a turn only just recognised as a `<task-notification>` is already in
its final shape when its `task_id` is read off the prompt. Only rows still
missing a link are touched, only a parse that adds something new is written,
and a value already on the row always wins over what the parse finds — so a
repeated `sync` converges once and then reports zero every time after,
exactly like the reclassify-on-growth and relink passes it runs alongside. A
sync's summary reports this as `task links: N row(s) linked to a background
task`. This is also how a database written before these columns existed (or
by hooks that predate them) gains its links, with no separate migration step:
the very first `sync`/`/audit-sync` after upgrading walks every existing
`tool_calls`/`turns` row once and fills in what the text already answers.

**In the viewer**: a tool call that carries a `task_id` gets a small "task:
<id>" chip in its detail and a distinct marker in the Flow view (see Flow
view, below); `task_id`/`run_ref` are shown verbatim in that call's expanded
body when set. There's no dedicated "background tasks" list of its own — the
linkage rides on the ordinary turn and tool-call views rather than adding a
new one.

### Sync (backfill)

Hooks only ever see turns from the moment they're installed forward. `sync`
fills in everything before that — and anything the hooks missed — by reading
transcripts already on disk, the same way `Stop` and `SessionEnd` do, just
over whole files instead of a byte-offset tail:

```
python3 audit_log.py sync [--workspace P | --all] [--db P] [--classify] [--projects-dir D]
```

**The audit is machine-wide, so `--all` is the default.** `--workspace` and
`--all` are mutually exclusive; naming neither means the same thing as
passing `--all` — every workspace `sync` can find gets swept in one run:

```
python3 audit_log.py sync --classify   # every workspace on the machine
```

A project directory under `~/.claude/projects` is named by a lossy slug of
its workspace path (`project_slug()` turns every non-alphanumeric character
into a dash), so a machine-wide sweep cannot just un-slug the directory name
back into a path — `-Users-mac-my-app` could equally be
`/Users/mac/my/app`, `/Users/mac/my-app`, or `/Users/mac/my.app`. Instead,
`discover_workspaces` recovers each one's real path from the transcripts
themselves (`probe_workspace`): every JSONL line already carries the
session's `cwd`, so it reads the newest few transcripts (`PROBE_FILES`,
newest-first, since an older file may predate the field or belong to a
since-renamed path) up to a few hundred lines each (`PROBE_LINES`) and takes
the first `cwd` it finds.

**Skip rules**: a project directory is left out of a machine-wide run, and
reported under `skipped:` with a reason, when:
- no transcript in it yields a recoverable `cwd` at all;
- the recovered workspace folder no longer exists on disk (deleted or moved
  since those sessions ran);
- it resolves to a workspace already claimed by another project directory
  (a duplicate — same real path, different slug history);
- the recovered workspace lives under the system temp directory — this is
  the plugin's own Haiku classifier scratch session (see
  `classifier_workdir`), which must never audit itself.

**`--workspace PATH`** narrows a run to one project instead: it resolves that
workspace's transcript directory the same way Claude Code does
(`project_slug()`) and syncs only its `*.jsonl` files. Use it to backfill (or
re-check) a single project without touching the rest of the machine.

For every workspace a run targets — one under `--workspace`, or all of them
by default — `sync` reads every `*.jsonl` directly under its transcript
directory (sibling subdirectories hold subagent traffic and per-session
metadata, not transcripts) and for each one upserts the session row,
assembles and persists every turn, scans and persists its subagents the same
way `Stop` and `SessionEnd` do (see Subagents, above), and archives a
verbatim copy of both the transcript and its subagent tree. A per-workspace
summary is printed as each one finishes, with an `agents:` line breaking
down how many agent rows were new, updated (a file that grew since last
scan), left unchanged, or tool-backfilled (an unchanged agent re-parsed only
to populate its `agent_tool_calls` rows — see Backfill trigger, above); a
machine-wide run then prints one grand total
block (`audit sync totals: N workspace(s)`) rolling up sessions, turns, tool
calls, agents, archives, reclassifications and relinked lineage rows across
every workspace it touched, plus the skipped directories and any
per-workspace failures — so one bad workspace (an unwritable `.claude/audit`,
a locked database) never aborts the rest of the sweep. The re-marked,
task-link, tool-tag, and (with `--classify`) classified counts sit below that
block rather than inside it, printed as `re-marked:`, `task links:`,
`tool tags:`, and `classified:` lines, since all four are DB-wide passes
(`finalize_db`) run once regardless of how many workspaces were swept: `tool
tags` reports how many `tool_calls`/`agent_tool_calls` rows
`backfill_tool_tags()` tagged and summarised (see Tool-call and task-spawn
tagging, above), and `classified` breaks down as `N haiku, N heuristic, N
synthetic, N agent(s)` — the same figures `classify_turn`/`classify_agent`
report per row, folded into one running total (see `--classify`, below).

**Every workspace a run targets lands in the same one database** — whatever
`--db`, `CLAUDE_AUDIT_DB`, or the machine-wide default resolves to (see What
it does, above). `sessions.workspace` is what tells them apart afterwards, so
filtering by workspace (in the viewer, or by hand) needs no separate files.
`--db` is not tied to `--all` — pairing it with a single `--workspace` just
redirects that one sync to a chosen file, which is how you get a
per-workspace database back:

```
python3 audit_log.py sync --workspace /path/to/project --db /path/to/project/.claude/audit/audit.db --classify
```

**Cursors are per-database.** `cursors` lives inside the database file
itself, so pointing two different `sync` runs at two different files (say, a
per-workspace `--db` and the machine-wide default) keeps a completely
independent cursor set in each — syncing the same session into both is safe
and non-interfering, since each file advances its own offset and neither one
sees the other's.

**`--classify`**: after the backfill, tag and title every still-untagged
turn (`tag IS NULL AND status != 'pending'`) in-process, one `classify_turn`
call per turn — no detached subprocess, since `sync` is already a foreground
CLI run and can afford to block. Synthetic turns are counted separately in
the summary output, since they get a title but never a tag. **Agents get the
identical treatment**, one `classify_agent` call per still-untagged row
(`tag IS NULL`, oldest `ts_start` first): `classify_agent` puts the subagent
to the model exactly as `classify_turn` puts a turn to it — the agent's own
spawning prompt (falling back to its `description` for a workflow step whose
prompt is empty) stands in for the prompt, its stored `result` for the
response — so it shares the same `TAG_TAXONOMY` rubric, the same
`CLAUDE_AUDIT_NO_LLM` heuristic fallback, and the same title rule a turn
gets; the only turn-only case is `is_synthetic`, since nothing spawns a
subagent by accident. This is one place `sync --classify` does more than the
live hooks did unprompted: `handle_stop`/`handle_session_end` already fire a
detached `spawn_agent_classifier` per newly-stored or still-untagged agent
the same way they do for turns (see Classification, below), so `--classify`
here is mainly the batch catch-all for anything that classifier never landed
on, plus the whole backfill of a database from before agent classification
existed. The summary's `classified` counts fold agents in as their own
`agent(s)` figure alongside the `haiku`/`heuristic`/`synthetic` breakdown (see
`print_workspace_summary`). **Tool-call tagging is untouched by this flag** —
it is deterministic and already complete or backfilled unconditionally by
every sync regardless of `--classify` (see Tool-call and task-spawn tagging,
below). **Whole-database passes run once per invocation, not once per
workspace**: re-marking synthetic turns, the tool-call tag backfill, the
background-task-link backfill, and (with `--classify`) tagging untagged turns
and agents are all DB-wide scans (`finalize_db`) over the one target
database, so a machine-wide run performs them exactly once, after every
workspace has been mirrored in — never once per workspace, which would
repeat the same scan over rows the sweep has already finished with.

**`--projects-dir`** (or the `CLAUDE_AUDIT_PROJECTS_DIR` environment
variable, which it overrides) points `sync` at a transcript root other than
`~/.claude/projects` — mainly so tests can point it at a scratch directory
of fixture transcripts instead of touching the real one.

**Idempotent**: turn persistence goes through the same
`prompt_uuid`-first matching `Stop`/`SessionEnd` use, so re-running `sync`
against a workspace that already has some or all of its turns logged only
adds what's missing — it never duplicates a turn, and an existing archived
transcript at least as long as the source is left alone. This makes `sync`
safe to run repeatedly: on a fresh machine as a one-time backfill, or
periodically as a catch-all for anything a killed session's `Stop` never
saw.

Every turn `sync` assembles is necessarily whole (the source file is closed,
not being appended to live), so persisted turns are marked
`status = 'swept'` rather than `'complete'` — the same status a
`SessionEnd`-only sweep gets.

The `/audit-sync` slash command (shipped in this plugin's `commands/`) wraps
this for interactive use — it runs

```
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/audit_log.py" sync --all --classify
```

as a machine-wide backfill into the central database and reports the
session/turn/classification counts back to the user.

### Merge (corporate restore)

`sync` backfills from transcripts still on disk; `merge` instead folds a
*separately backed-up database* into a live one:

```
python3 audit_log.py merge --from BACKUP.db [--db DEST]
```

**The story this exists for**: a machine gets wiped and rebuilt — a VM
reimage, a disk replacement, a fresh account — and the central audit
database goes with it. The hooks start logging again from nothing the moment
Claude Code next runs there, but everything recorded before the wipe only
still exists in whatever backup was taken of the old `audit.db`. Restoring it
is one of two moves, depending on whether anything has been logged on the
rebuilt machine yet:

- **Destination is empty** (the rebuild is fresh and nothing has run there
  yet, or the audit directory doesn't exist at all): just copy the backup
  file into place —
  `cp BACKUP.db ~/.claude/audit/audit.db` — there is nothing yet to
  reconcile it with, so a byte-for-byte restore is both correct and the
  fastest path. `merge` is not needed for this case.
- **Destination already has data** (the machine has been logging fresh
  sessions since the rebuild, before the backup was restored): copying the
  file over would erase those new sessions. Run `merge --from BACKUP.db`
  instead — it folds the backup in row by row *without* touching or
  discarding anything the live database has already recorded since.

**WAL sidecar note**: these databases run in WAL mode, and a WAL reader
normally needs a writable `-shm` companion next to the `.db` file — but a
backup is usually just the `.db` file alone, since `-wal`/`-shm` hold
not-yet-checkpointed writes that most backup tooling doesn't think to copy.
`open_source_db` handles this by trying a plain read-only open first, then
falling back to SQLite's `immutable=1` mode, which reads the file without
needing a `-shm` at all — at the cost of ignoring a `-wal` file if one
*does* happen to be sitting next to the backup, since `immutable` promises
SQLite the whole file will not change. For a fully lossless backup, checkpoint
the source database before copying it out —
`sqlite3 audit.db "PRAGMA wal_checkpoint(TRUNCATE);"` — so every committed
row lives in the `.db` file itself and nothing is left stranded in a `-wal`
the backup won't include. Either way the source is opened strictly
`mode=ro`: the merge can never alter, upgrade, or checkpoint the backup file
it was handed.

**How rows are matched**: `turn_id` is an `AUTOINCREMENT` rowid private to
each database, so the same turn almost certainly has different ids on the
two sides. `prompt_uuid` is a turn's real identity (the `uuid` Claude Code
gave the prompt line), so turns are matched on that, and a
source-turn-id → destination-turn-id map is built as they're matched;
`tool_calls.turn_id` and `agents.turn_id` are rewritten through that map as
each table is imported. Sessions match on `session_id`, agents on
`(session_id, agent_id)`.

**Neither side is authoritative — the merge is per-row, keeping whichever
version is more complete**, so that merging the same backup twice is a
no-op (every comparison is strict `>`, so an equal row never gets rewritten
on a second pass):
- **Sessions**: the live row wins outright, except that a `NULL`
  `ended_at`/`end_reason` is back-filled from the backup — the one case a
  live session's row can know less than a backup's.
- **Turns**: ranked by `turn_completeness` — finished `status` first
  (`pending` < `swept` < `complete`), then whether it was ever classified,
  then response length — so a turn the live database only half-captured
  loses to a fuller version from the backup, and vice versa.
- **Agents**: `src_bytes` (the size of the parsed agent transcript) decides,
  since a finished agent file is append-only and only ever grows — the
  bigger parse saw more. Whichever side's agent row wins takes its
  `agent_tool_calls` rows with it wholesale (keyed by `(session_id, agent_id)`
  — the `agents` primary key on both sides, so nothing needs remapping the way
  `turn_id` does), so a turn's flow is never a mix of the two parses; a table
  missing on one side of the merge (a backup old enough to predate it) simply
  leaves the destination's rows as they are.
- **Cursors**: only imported for a session the destination has no cursor
  for at all; a live cursor mid-transcript always wins, since that transcript
  is still being appended to on this machine.
- A source turn with no `prompt_uuid` at all (a `pending` row a
  `UserPromptSubmit` hook opened that no transcript sweep ever reached) has
  nothing to match by and is skipped — importing it would just duplicate it
  on the next merge — and counted as `turns_unkeyed` in the report.

Merging is schema-tolerant: every query is built from the intersection of
columns the two databases actually have (`shared_columns`), so a backup from
an older release (missing a column the live schema has since gained, or
carrying one it no longer does) still merges correctly instead of erroring.

## The service

`service.py` puts the viewer behind a real `http://` origin instead of
a `file://` page, which is what lets the browser pull a *consistent* snapshot
of a database that a hook may be writing to at the same moment, get pushed a
refresh the instant that happens, and open the bytes of a file a turn
touched — none of which a page loaded from disk can do. For ordinary use it
changes nothing about what's logged; it's a way of looking at the same
`audit.db`. The one deliberate exception is `POST /api/merge`, which lets the
viewer's own **Merge database…** button fold a backed-up `audit.db` into the
live one without dropping to a terminal (see `/api/merge` and Merge database
UI, below).

It binds `127.0.0.1:4737` by default — override the port with
`CLAUDE_AUDIT_PORT`, never the host (see Security, below) — and resolves the
database exactly the way `audit_log.py` does: `CLAUDE_AUDIT_DB`, else
`~/.claude/audit/audit.db`. Its pidfile and logs (`service.log`,
`service-errors.log`) live beside whatever database it's serving, the same
way `hook-errors.log` does.

### Endpoints

Every route below is `GET` except one, and every response — including the
framework's own error pages — carries `X-Content-Type-Options: nosniff`. A
`POST` to any `GET`-only route (or a `GET`/`HEAD` to `/api/merge`) gets a
`405` naming the methods it does accept, rather than a bare `404`:

| Endpoint | Method | Returns |
|---|---|---|
| `/` | GET | the audit viewer (`viewer.html`) |
| `/view` | GET | the artifact renderer (`fileview.html`), given `?path=` |
| `/api/health` | GET | `{ok, version, db, port}` |
| `/api/db` | GET | a consistent snapshot of the audit database |
| `/api/events` | GET | Server-Sent Events; a `db-change` event whenever the database moves |
| `/api/files` | GET | files touched by `Write`/`Edit`/`NotebookEdit`/`MultiEdit`, optionally `?turn=<id>` |
| `/api/file` | GET | one file's raw bytes, given `?path=`, only from inside a workspace the database has recorded |
| `/api/merge` | POST | folds an uploaded audit database into the live one — the service's one write endpoint (see below) |

**`/api/db` snapshot semantics**: straight-copying a live WAL database can
capture a half-applied write, or miss the `-wal` file entirely, and hand the
browser something `sql.js` refuses to open. Instead `/api/db` opens the
database read-only and copies it via SQLite's own online **backup API**
(Python's `sqlite3.Connection.backup()`), which takes the same lock SQLite
itself would, into a fresh temp file — so the copy served is always a single
coherent point in time, never a torn write. That temp file is streamed back
as `Content-Disposition: attachment; filename="audit.db"` with
`Cache-Control: no-store`, then deleted; a fresh call always re-snapshots
rather than reusing anything.

**`/api/events` (SSE, live refresh)**: one long-lived response per browser
tab, chosen over WebSockets because the payload is a single one-way "go
re-fetch" signal, `EventSource` reconnects on its own, and it costs no
dependency (the service is stdlib-only). Once a second it compares a cheap
change signal — `PRAGMA data_version` (SQLite's own "has anything committed
since I last looked") plus the `.db` and `-wal` files' own mtime/size, as a
fallback for what `data_version` can't see, such as the file being swapped or
a backup restored over the top — against what it saw last, and on a
difference emits `event: db-change`. A comment-line keepalive goes out every
15s so an idle connection isn't mistaken for dead by a proxy, and a database
that doesn't exist yet is polled the same way, emitting `db-appeared` the
moment one shows up.

### `/api/merge` — the one write

`POST /api/merge` is the single exception to "reads are the rule": it lets
the viewer's own **Merge database…** button (see Merge database UI, below)
fold a backed-up `audit.db` into the live one without a terminal, by driving
the exact same engine `audit_log.py merge --from` does — there is no second
implementation of the merge rules to drift out of sync with the CLI.

- **Body**: the uploaded database's raw bytes, either as
  `application/octet-stream` or as the first file field of a
  `multipart/form-data` upload — a hand-rolled streaming parser reads just
  that one part and discards anything after it, so the request body is never
  held in memory whole. `Content-Length` is required (chunked transfer is
  refused with `411`, since the point of a declared length is refusing an
  oversized upload before reading it) and capped at **512 MiB**, checked
  against the declared length up front and again against what was actually
  received.
- **Cross-site upload guard.** Binding loopback is not, by itself, an
  authorization boundary in a browser: any page in any tab can `POST` a form
  to `http://127.0.0.1:4737` without tripping CORS, because a form
  submission is never preflighted. `/api/merge` refuses the request when
  `Origin` is present and isn't this service's own origin, and again when
  `Sec-Fetch-Site` says the request crossed a site boundary — neither header
  is sent by `curl` or a same-origin `fetch`, so this closes the browser
  attack without inconveniencing either.
- **Spooled beside the database, never in a workspace.** The body streams
  straight to a temp file in `merge-incoming/`, a subdirectory next to the
  database itself — never the system temp directory, and never anywhere a
  workspace lives — and that file is deleted on every exit path: success, a
  refused upload, or a crash mid-merge. Every request also sweeps any spool
  file older than an hour, left behind by a process that was killed before
  it could clean up after itself.
- **Validated three ways before it goes anywhere near the merge**: the first
  16 bytes must be the SQLite magic header, the file must open read-only
  (via `open_source_db()` — the same `immutable=1` fallback the CLI's
  `merge` uses for a WAL-less backup), and it must have `sessions` and
  `turns` tables. Any failure is a `400` naming which check failed, and
  nothing reaches `merge_databases()`.
- **Ingests only through the merge engine.** The endpoint imports
  `audit_log.py` by path and calls its `open_source_db()` / `open_db()` /
  `merge_databases()` directly — the identical functions
  `audit_log.py merge --from` calls — so the row-matching, most-complete-wins
  and schema-tolerant rules described under Merge (corporate restore), above,
  are exactly the rules this endpoint applies too.
- **One merge at a time.** A process-wide lock serializes only the merge
  step itself (the upload and validation ahead of it can proceed in
  parallel); a second request that arrives while one is committing waits up
  to 5s and then gets a `409` to retry, rather than the two interleaving
  writes against the same rows.
- **Response**: `200` with a JSON summary — per-table `{imported, replaced,
  skipped}` counts for sessions/turns/tool_calls/agents/agent_tool_calls/
  cursors, a `totals` roll-up, `received_bytes`, `elapsed_s`, and the raw
  `counts` dict `merge_databases()` returns, unrearranged, for a caller that
  would rather read the engine's own vocabulary than this endpoint's summary
  of it. Merging the same backup twice reports everything `skipped`, for the
  same reason a second `sync` or CLI `merge` does: every comparison is
  strict `>`.
- The merge commits on a connection of its own, which moves both `PRAGMA
  data_version` and the file's mtime — so `/api/events` emits `db-change` on
  its next tick exactly as it would for a hook's write, and any open viewer
  tab refreshes itself without needing to know a merge happened at all.
- A traceback from anywhere in this path follows the same rule as every
  other endpoint: it goes to `service-errors.log` beside the database, and
  the caller gets a generic, non-identifying message.

### Watchdog

Hooks don't just log; they keep this service alive. `ensure_service()` in
`audit_log.py` runs at the very **end** of both the `Stop` and `SessionEnd`
handlers — after the turn is already durably written, since the audit never
depends on the viewer. It does one cheap loopback connect to the service
port; if anything is already listening, it does nothing, and otherwise it
spawns `service.py serve` detached (`start_new_session=True`, so it outlives
the hook process and keeps running after the CLI exits). Like every hook code
path it never raises and never blocks longer than its connect timeout — a
missing viewer must never fail the turn it's riding along on. Set
**`CLAUDE_AUDIT_NO_SERVICE=1`** to opt out entirely: with it set, the
watchdog probe never runs and nothing is ever spawned.

Outside of hooks, the service also has its own small CLI for manual control:
`python3 service.py start` (idempotent — spawns detached and waits for
`/api/health`, or reports `already_running: true`), `status`, and `stop`
(`SIGTERM`, escalating to `SIGKILL` if it doesn't exit).

### Running at login (`install-startup` / `uninstall-startup` / `print-startup`)

The watchdog only starts the service the next time a hook fires. To have it
already running before that — at login, or after a reboot —
`install-startup` registers it with the OS's own supervisor:

- **macOS**: writes a **LaunchAgent** plist to
  `~/Library/LaunchAgents/com.claude-audit.service.plist` and loads it with
  `launchctl bootstrap` (falling back to `launchctl load -w` if bootstrap
  refuses), `RunAtLoad`, and `KeepAlive={"SuccessfulExit": false}` — restart
  on a crash, but respect a clean `stop` (an exit code of 0 means it was told
  to go away, not that it died).
- **Linux**: writes a **systemd user unit** to
  `~/.config/systemd/user/claude-audit.service` and runs
  `systemctl --user enable --now`, with `Restart=on-failure` /
  `RestartSec=5`.

Either way, an explicit `--db`/`--port` is baked into the unit's own
environment (`EnvironmentVariables` on macOS, `Environment=` lines on Linux)
because a login agent inherits almost nothing from an interactive shell — a
service started this way would otherwise silently serve a different database
than the one the shell resolves. `uninstall-startup` reverses the same steps
(`launchctl bootout` / `systemctl --user disable --now`) and deletes the
plist/unit file. `print-startup` prints the plist/unit text to stdout without
installing anything — plain text by default (so `print-startup > file` is
byte-for-byte what would be installed), or `--json` for
`{path, text, label, log, error_log, python, script}` for a config-management
pipeline to consume instead.

### Security

- **Loopback-only bind.** `BIND_HOST` is hard-coded to `127.0.0.1` and is
  *not* configurable by any flag or environment variable — this process hands
  out file bytes and a full prompt/response history, and binding anything
  else would publish one machine's entire audit trail to its network.
- **Workspace-root allowlist, not configuration.** `/api/file`'s only
  authority is `SELECT DISTINCT workspace FROM sessions`, realpath'd, from
  the database being served — nothing is separately configured, a workspace
  of `/` is explicitly refused rather than honoured, and the set is re-read
  every 30s so a session started after the server came up becomes servable
  without a restart. A request is realpath'd the same way before the check,
  so a `..`, a symlink out of the workspace, and a bare `/etc/passwd` all
  collapse to the same test — and a miss returns an identical, deliberately
  uninformative 403 whether the path is outside every workspace or simply
  doesn't exist, so the endpoint can't be used to probe the filesystem for
  what exists.
- **Exactly one write endpoint, and it is narrowly scoped.** Every other
  route is `GET`; the service never inserts, updates, deletes, classifies, or
  migrates anything outside of it — those remain otherwise CLI-only
  operations on `audit_log.py`. `POST /api/merge` (see `/api/merge`, above)
  is the deliberate exception: it is loopback-only like everything else
  here, refuses a cross-origin or cross-site upload before reading a byte,
  caps and validates the upload three ways (SQLite header, a real read-only
  open, the `sessions`/`turns` tables) before it is allowed near a merge, and
  the only thing it can then do to the database is hand the validated bytes
  to `audit_log.merge_databases()` — the identical, per-row,
  most-complete-wins engine `audit_log.py merge --from` runs from the CLI,
  never a bespoke write path of its own. An upload is spooled beside the
  database, never inside a workspace, and the spool file is deleted on every
  exit path regardless of how the request ends. `/api/file` additionally
  refuses directories and anything that isn't a regular file.
- A raw HTML file opened directly (the "Raw" link, or `/api/file` hit
  outside `fileview.html`'s iframe) carries
  `Content-Security-Policy: sandbox allow-scripts allow-downloads`, so it
  can't run on this origin and reach back into `/api/db` — defence in depth
  on top of the sandboxed iframe `fileview.html` normally renders it in.
- A traceback names source paths and internals, so it is never sent down the
  wire: it goes to `service-errors.log` beside the database, and the caller
  just gets a generic `500 internal server error`.

## Install

This is a Claude Code **plugin**. The repo that contains it
(`claude-code-tools`) doubles as a plugin marketplace
(`.claude-plugin/marketplace.json` at the repo root), so installing is:

```bash
claude plugin marketplace add <git-url-or-local-path-of-claude-code-tools>
claude plugin install claude-audit@claude-code-tools
```

(or interactively via `/plugin`). The plugin registers the three hooks
automatically from `hooks/hooks.json` — no manual `settings.json` editing —
and adds the `/audit-sync` command. Requires `python3` on PATH (stdlib only)
and the `claude` CLI for Haiku classification.

For local development without installing:

```bash
claude --plugin-dir ./plugins/claude-audit
```

The layout inside the plugin:

```
plugins/claude-audit/
├── .claude-plugin/plugin.json   # manifest
├── hooks/hooks.json             # UserPromptSubmit / Stop / SessionEnd
├── commands/audit-sync.md       # the /audit-sync command
├── scripts/
│   ├── audit_log.py             # the logger (this document's subject)
│   └── service.py               # the local viewer service (see The service)
└── views/
    ├── viewer.html               # the viewer -- standalone, or served live
    ├── fileview.html             # artifact renderer, served only via service.py
    └── sample.db                 # demo database for the standalone viewer
```

The `SessionEnd` hook gets an explicit 30s timeout because it does more work
than the others (transcript sweep + transcript archive copy) and runs while
the session is tearing down.

**Hooks are snapshotted at session start.** Editing `settings.json` while a
session is already running has no effect on it — start a new Claude Code
session for the hooks to take effect.

## Schema

SQLite, WAL mode, **one shared database for the whole machine** at
`~/.claude/audit/audit.db` by default (override with `CLAUDE_AUDIT_DB` or
`--db`) — or one DB per workspace, at
`<workspace>/.claude/audit/audit.db`, when a workspace-scoped `--db` is used
instead (see What it does / Sync, above); nothing in the schema itself is
per-workspace, since `sessions.workspace` already tells them apart either
way.

**`sessions`** — one row per Claude Code session
- `session_id` (PK), `workspace`, `git_branch`, `cc_version`
- `started_at`, `ended_at`, `end_reason`

**`turns`** — one row per completed prompt turn
- `turn_id` (PK), `session_id` (FK), `prompt_id`, `prompt_uuid` (unique)
- `ts_start`, `ts_end`, `duration_s`, `model`, `permission_mode`
- `prompt`, `response` (assistant text, tool calls stored separately)
- `tag` — one of the seven-entry taxonomy (`plan`/`build`/`fix`/`validate`/
  `docs`/`ops`/`chat`) for a genuine human turn, or a deterministic
  `system:*` kind for a synthetic one (see What it does, above); nullable
  until classified. Plain `TEXT`, **not** `CHECK`-constrained — see the
  permissive-constraint rationale under What it does, above — so the
  taxonomy in `TAG_TAXONOMY` can grow or change without a schema migration.
- `title` (one-sentence summary, ≤80 chars), `tag_source` (`haiku`,
  `heuristic`, or `system` for a synthetic turn's deterministic kind)
- `is_synthetic` (0/1, default 0) — set when the prompt was machine-generated
  rather than typed by a person: an interrupt notice, a slash-command
  expansion, or harness-injected context (see `SYNTHETIC_PREFIXES` /
  `SYNTHETIC_MARKERS` in `audit_log.py`). These turns are still logged in
  full but never tagged, and the viewer hides them by default.
- `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`, `thinking_tokens`
- `status` (`pending` → `complete` on `Stop`, or `swept` if only `SessionEnd`
  or `sync` ever saw it)
- `parent_uuid`, `last_uuid` — the transcript's own linked-list pointers:
  `parent_uuid` is the prompt line's `parentUuid`, `last_uuid` is the `uuid`
  of the turn's final main-thread line. `B.parent_uuid == A.last_uuid` makes
  B a child of A; two turns sharing a `parent_uuid` are a **fork** (a rewind,
  an edited-and-resubmitted prompt, a branching `/resume`); a `NULL` or
  unmatched `parent_uuid` makes a turn a root. See Turn lineage, above, and
  the viewer's Flow view, below. Indexed (`idx_turns_parent_uuid`,
  `idx_turns_last_uuid`) since the viewer's lineage lookup is a `last_uuid`
  match per row.
- `task_id` — set only on the synthetic turn born from a
  `<task-notification>` prompt: the id of the background task (a `Bash`
  background run, an `Agent` spawn, or a `Workflow` run) that just finished.
  `NULL` on every ordinary turn. See Background tasks, above. Indexed
  (`idx_turns_task_id`).

**`tool_calls`** — one row per tool invocation within a turn
- `tool_call_id` (PK), `turn_id` (FK), `seq` (order within the turn)
- `tool_name`, `tool_use_id`
- `input_json` (truncated to 10,000 chars, `input_truncated` flags this)
- `result_text` (truncated to 10,000 chars, `result_truncated` flags this), `is_error`
- `task_id`, `run_ref` — set only on a `Bash`/`Agent`/`Workflow` call whose
  result names a background task (see Background tasks, above): `task_id` is
  the id a matching `<task-notification>` turn will carry, `run_ref` a second
  reference (a workflow run id or an `agentId`) into `agents`. `NULL` on every
  other call, and on these three tools too until their result actually
  contains one. Indexed on `task_id` (`idx_tool_calls_task_id`).
- `tag`, `summary` — one of the seven `TAG_TAXONOMY` tags and a one-line
  human-readable summary, assigned deterministically (no model call) from the
  call's own `tool_name` and `input_json` by `tool_tag_and_summary()` at
  capture time, and backfilled the same way for any row that predates the
  columns (see Tool-call and task-spawn tagging, above). Never `NULL` on a
  row written after this shipped or touched by a `sync`.

**`agents`** — one row per subagent (Task agent or workflow step) spawned by a
turn, read from the sidecar transcripts in
`<projects>/<slug>/<session_id>/subagents/`
- `session_id` + `agent_id` (composite PK)
- `turn_id` (parent turn, NULL until resolvable), `prompt_id` (the parent
  turn's prompt id, which is the join key carried on every agent line)
- `tool_use_id` (the spawning tool call, from the agent's `meta.json`)
- `workflow_id` (the `workflows/<run>/` directory for a workflow step, else
  NULL), `agent_type`, `description`, `model`
- `prompt` (the instruction it was spawned with) and `result` (its final
  answer, or its `StructuredOutput` payload as JSON) — each truncated to
  10,000 chars
- `ts_start`, `ts_end`, `duration_s`, the same five token columns as `turns`,
  and `tool_call_count` — a *count* of the tool calls the agent made (the
  calls themselves, individually, are `agent_tool_calls` — see below)
- `src_bytes` — the size of the parsed JSONL, so a re-scan skips unchanged
  agents without reparsing them
- `tag`, `title`, `tag_source` — the same three columns a turn carries,
  filled in by `classify_agent` against the identical `TAG_TAXONOMY` and
  Haiku/heuristic machinery a turn uses (see Classification, above, and the
  tagging hierarchy under What it does, above); nullable until classified,
  and dropped back to `NULL` by `carry_classification()` if a re-parse ever
  changes the agent's stored `prompt`/`result` out from under an existing tag.

`agents` shipped after the first release too, but as a whole new table
(`CREATE TABLE IF NOT EXISTS`) rather than an `ALTER`-added column, so it
appears in an older database the moment it's next opened — no rebuild needed.

**`agent_tool_calls`** — one row per tool invocation within a subagent's own
transcript, the `tool_calls` of `agents` (see Subagents / `agent_tool_calls`,
above, for extraction and the backfill trigger)
- `atc_id` (PK), `session_id` + `agent_id` (the `agents` composite key — not a
  foreign key of its own, just the join), `seq` (order within the agent's run)
- `tool_name`, `tool_use_id`
- `input_json` (truncated to 10,000 chars, `input_truncated` flags this)
- `result_text` (truncated to 10,000 chars, `result_truncated` flags this), `is_error`
- `tag`, `summary` — identical in meaning and derivation to `tool_calls.tag`/
  `summary` above; the same `tool_tag_and_summary()` call tags a subagent's
  own calls, so its flow reads by the same vocabulary a turn's does.

Also a whole new table rather than an `ALTER`, so it appears the moment an
older database is next opened; unlike `agents` it needs an explicit backfill
pass (a `sync`/`/audit-sync`, or the live hooks re-parsing an agent that grows)
before an agent logged under an older release has rows in it — see Backfill
trigger, above.

**`cursors`** — one row per session: `session_id` (PK), `byte_offset`,
`updated_at`. Tracks how far each session's transcript has been read.

**`meta`** — key/value store (`schema_version`, `created_at`).

Indexes on `turns(session_id)`, `tool_calls(turn_id)`, `agents(turn_id)` and
`agent_tool_calls(session_id, agent_id)`.

`is_synthetic`, `input_truncated`, `parent_uuid`/`last_uuid`,
`tool_calls.task_id`/`run_ref` plus `turns.task_id`, the `tag`/`summary` pair
on both `tool_calls` and `agent_tool_calls`, and `agents.tag`/`title`/
`tag_source` were all added after the first release; since SQLite has no
`ADD COLUMN IF NOT EXISTS`, `audit_log.py` attempts each migration on every DB
open and treats the "duplicate column" error as the success case for a
database that already has it (see `MIGRATIONS` in `audit_log.py`).
`viewer.html` does the equivalent on the client side before querying, so
older databases opened in the viewer degrade
gracefully instead of erroring — a database without `parent_uuid`/`last_uuid`
still opens fine, its Flow view just falls back to drawing turns in
chronological order instead of by lineage, one without `task_id`/`run_ref`
simply never shows a background-task marker, and one without the tool-call
`tag`/`summary` pair just shows an untinted node with the tool name as its
label instead of a tag chip and summary line (see Viewer usage, below). A
fresh `sync` over an older database backfills all of it: the new lineage
columns from the transcripts themselves (see Relinked backfill, above), the
background-task links and the tool-call tags from text already stored in the
database (see Background tasks / Sync backfill pass, and Tool-call and
task-spawn tagging, above), and agent tags via `--classify` — no separate
migration step is needed for any of it.

## Pricing

Every cost figure anywhere in the viewer — a turn's tooltip, an agent's
tooltip, every number in the Dashboard view (see Dashboard view, under Viewer
usage, below) — comes from one function, `estCost()` in `viewer.html`, so a
per-row number and the aggregate it rolls up into can never drift apart by
being computed two different ways.

**The audit log records tokens, not invoices.** A turn or agent is priced
against a rate table embedded in `viewer.html` itself — never fetched live,
so the page still works from a bare `file://` URL with no network at all —
and every dollar figure the page shows is explicitly an *estimate*: the
database has no idea what was actually billed, and a Claude subscription has
no per-token dollar billing at all (see the est.-only caveat, below). This is
stated once, in `costTip()`, and reused as the hover title on every cost
figure and estimate chip on the page rather than repeated inline everywhere a
number appears.

**Two provider rate maps, embedded and dated.** `PRICING.providers` holds two
maps, `anthropic` and `vertex_ai`, each USD per 1,000,000 tokens for every
model the log can see, keyed by the shared `PRICING.as_of` date the rates
were read off the official pages ("2026-09-22" as of this writing) and backed
by `PRICING.sources` — the Anthropic pricing page and the Google Cloud
Vertex AI pricing page's Global-endpoint table for Claude models. Both the
as-of date and the source links are shown verbatim in the "Rates, sources &
notes…" modal, so any number on screen can be checked against where it came
from. A list of researched notes (`PRICING.notes`) documents the caveats
behind the numbers: Vertex's Global endpoint prices equal Anthropic's
first-party rates, while Vertex regional/multi-region endpoints are all
first-party rates ×1.1 (applied by `activeRates()` when "regional /
multi-region" is selected); a couple of models carry a non-standard
cache-read rate; one model id's exact API name wasn't printed on the pricing
page and is flagged to confirm before relying on it; thinking tokens are
billed as output, and since this audit DB already counts `thinking_tokens`
inside `output_tokens`, `estCost()` never adds them a second time; one model
family isn't offered on Vertex at all, and an older Vertex snapshot id uses
an `@<date>` suffix that normalization strips (see below); and the Batch
API's 50%-off rate isn't modeled, since audit traffic is interactive rather
than batched.

**Model-id matching is prefix-based, not exact, so a dated or region-qualified
id still resolves.** `normModel()` lower-cases an id and strips the parts
that vary without changing the price — a Vertex `@YYYYMMDD` version suffix, a
`publishers/anthropic/models/` path prefix, a Bedrock cross-region prefix
(`us.`/`eu.`/`apac.`/`global.`) or an `anthropic.`/`anthropic/` prefix, a
Bedrock `-v1:0` suffix, a trailing `-latest`, and a trailing `-YYYYMMDD`
snapshot date — before `rateFor()` matches it against the active table.
Matching then picks the **longest** rate-table key that is a prefix of (or an
exact match for) the normalized id, so `claude-fable-5-1` wins over the
shorter `claude-fable-5` for an id that starts with both, and a dated id like
`claude-haiku-4-5-20251001` still resolves to the `claude-haiku-4-5` row
after normalization.

**A third option, Custom, replaces the table entirely.** Picking "Custom" in
the Dashboard's pricing selector seeds a copy of whichever provider it was
last showing (`seedRateMap()`, tracked as `pricing.seed`) into an editable
table — one row per model, five numeric fields (input, output, cache read,
cache write 5m, cache write 1h) in USD per 1,000,000 tokens — with per-cell
validation (a malformed or empty box is treated as a typo and put back to its
previous value, never silently priced at zero), a "Reset to Anthropic API /
Vertex AI" button, and an Export/Import JSON round-trip. `sanitizeRateMap()`
backs both the import box and the `localStorage` restore path: it coerces
every value to a finite, non-negative number and tolerates a bare rate map, a
`{rates: {...}}` wrapper, or a whole exported provider block, so a
hand-pasted table can never inject anything but numbers into the page. The
chosen provider, endpoint, seed, and the custom table itself are all
remembered per browser in `localStorage` (`cc-audit-price-*`), restored on
load, and never sent anywhere — a remembered "custom" selection with nothing
actually stored under it falls back to the provider it was seeded from,
rather than silently pricing everything at zero.

**An unpriced model is excluded from every total, never billed as $0.** When
`rateFor()` finds no rate-table key that matches a model at all,
`estCost()` returns `priced: false` and that row's tokens are tracked
separately (as `unpricedTokens`, broken down by model name in `unpriced`)
instead of being folded into the cost total at zero, which would understate
it without saying so. The Dashboard surfaces this loudly, above every other
figure on the page: a warning chip names each unpriced model and how many
tokens it accounts for before any total is read. The same rule holds for an
individual turn's or agent's cost tooltip elsewhere in the viewer, which
shows nothing rather than "$0" when its model isn't in the active table.

**The est.-only caveat, for subscription users especially.** The Dashboard's
pricing bar, every cost tooltip (`costTip()`), and the rates modal all state
the same thing: cache writes are assumed to be 5-minute writes because the
audit log doesn't record which TTL a given write used; thinking tokens are
already inside `output_tokens` and are never counted a second time; and, most
importantly, a Claude **subscription** (Pro/Max, as opposed to metered API
billing) has no per-token dollar cost at all — for anyone on a subscription,
every figure this page prices is a *comparison scale* between turns, tags,
workspaces and models, useful for seeing which kind of work is relatively
expensive, and never anything that resembles an actual bill.

## Viewer usage

`viewer.html` works two ways, and is exactly the same page either way — it
probes for a local service on load and switches modes, nothing to configure:

- **Standalone**: open it directly in a browser (double-click, or `file://`).
  It loads `sql.js` (SQLite compiled to WASM) from the cdnjs CDN on first
  use, then everything else runs locally in-page: nothing about the DB's
  contents leaves the browser. Pick a database either by clicking the file
  picker or by dragging a `.db` file onto the page. You only need `audit.db`
  itself — the `audit.db-wal` and `audit.db-shm` WAL sidecar files (if
  present next to it) can be ignored; they hold not-yet-checkpointed writes
  and aren't needed to read the committed data sql.js loads.
- **Service mode**: open `http://127.0.0.1:4737/` (or wherever
  `service.py` is listening — see The service, above) instead, and the page
  auto-loads the live database with no file picking at all, then keeps
  itself in sync as it changes. See Service mode, below.

Everything in this section beyond Service mode — totals, tag filtering, the
turn list, Files touched, Flow, Dashboard — is identical in both modes; only
how the database gets into the page differs.

Once loaded you get: summary totals (turn/session/token counts), a
per-tag breakdown (plan/build/fix/validate/docs/ops/chat/untagged) you can
click to filter,
a session/workspace list, and a searchable turn list where each row expands
to its full prompt, response, and tool-call trace. Prompt, response, and
agent prompt/result text renders as Markdown (see Markdown rendering, below).
Each entry in a tool-call trace leads with a **tag chip** (the same
plan/build/fix/validate/docs/ops/chat colors a turn's own chip uses) followed
by the tool name and the logger's one-line **summary** as the headline — see
Tool-call and task-spawn tagging, above — with the usual error/truncated
flags after it; a database from before those columns existed just shows the
tool name with no chip or summary, exactly as it always did. A truncated tool
input is flagged in that trace the same way a truncated result already is.
When the database has an `agents` table, the summary totals also include an
**Agents** stat (a DB-wide count of every row in `agents` — it's not affected
by the hide-system-turns toggle, since agents hang off turns only loosely).
A turn row that spawned any agents shows an "N agent(s)" badge in its list
entry, and its detail panel gets an **Agents** section listing each one. A
classified agent (see Subagents / Classification, above) leads its summary
line with its own tag chip and its written title, in place of the bare
`agent_type`, which moves down to the meta line alongside model, duration,
token counts and tool-call count; an unclassified agent — every row in a
database from before agent classification existed — reads exactly as it
always did, titled by `agent_type` (falling back to the first line of its
prompt as the description). Expanding an entry shows the full prompt and
result text. Agents spawned as part of one workflow run are grouped together
under that run's id rather than scattered across the list. Clicking an agent
(in this list, or as a node in Flow — see below) opens its own modal with the
same prompt/result plus a **Tool calls** section: every call the agent made,
in the order it made them, rendered by the identical component the turn
detail's own tool-call trace uses, tag chip and summary included — so a
sub-agent's flow reads exactly like a turn's, input/output/error/truncation
flags and all. When the database has `agent_tool_calls` rows but this
particular agent predates the backfill that populates them (see Subagents /
Backfill trigger, above), the section falls back to reporting its
`tool_call_count` with a note to run `/audit-sync`, rather than showing
nothing or claiming it made no calls. All of this degrades gracefully — an
older database with no `agents` table (or no `agent_tool_calls` table) simply
shows none of it.

**Markdown rendering**: a turn's prompt and response, and an agent's prompt
and result, are authored as Markdown, so `viewer.html` renders them as
Markdown wherever they appear — the turn detail, the Agents section, and
every modal — through the identical pipeline `fileview.html` uses for a
`.md` file (see `/view`, below), byte for byte: `marked.parse` →
`DOMPurify.sanitize` (`USE_PROFILES: { html: true }`) → the container's
`innerHTML`, with any fenced code block then run through `highlight.js` and
every link rewritten to open in a new tab with
`rel="noopener noreferrer nofollow"`. That sanitized container is the *only*
`innerHTML` sink anywhere in `viewer.html` — every other piece of database
text still reaches the page through a text node, exactly as before rich text
existed. Each rendered section carries a small **raw** toggle that swaps it
for the plain, unrendered `<pre>` the page has always shown, and back
again — the two never both show at once, and the toggle's own label
(`raw`/`rendered`) says which one is up. **Offline fallback**: if `marked`,
`DOMPurify`, or `highlight.js` fails to load at all — no network, a `file://`
page, a blocked CDN extension — or a render call throws for any reason, that
section silently stays on its plain `<pre>`, with no toggle and no error
shown; rendering is checked once (`mdReady()`) rather than assumed, so a
partial CDN failure degrades one section at a time instead of breaking the
page.

**Hide system turns** (checked by default) filters synthetic turns
(`is_synthetic = 1`) out of the list, the totals, and the per-tag counts —
interrupt notices and slash-command expansions clutter a read of "what did
this session actually do" without adding anything, though they're always in
the database and one click away if you need them; a synthetic turn that's
shown is marked with a small "system" tag next to its title. The toggle (and
every count it affects) only applies where the loaded database actually has
an `is_synthetic` column — against an older database without it, the viewer
falls back to showing everything.

**Workspace filter**: a "Workspaces:" line above the totals always lists
every workspace the open database tracks — DB-wide, ignoring the current
filter, so it answers "what does this file actually cover" regardless of
what's selected. When it tracks more than one — the ordinary case for the
machine-wide default database, since every workspace's turns land there,
though nothing stops a workspace-scoped or `merge`d file from having several
too — a **workspace dropdown** appears next to the
search box, one entry per distinct `sessions.workspace` value, each labelled
by that folder's own name (its path's basename) with a session count and the
full path as a hover tooltip, so two differently-located folders that happen
to share a name are still told apart on hover. Picking one narrows the
turn list, totals, tag counts, and session list to that workspace only; "All
workspaces (N)" clears it. The selection is remembered per browser (via
`localStorage`, so it never leaves the machine) and re-validated against
whatever database is opened next, falling back to "All" if that workspace
isn't in it. Against a database with only one workspace, or an older one
with no `sessions.workspace` column, the dropdown is hidden rather than
shown with nothing to choose between.

**Flow view**: a **List / Flow** toggle next to the workspace and session
selectors switches from the turn list to a node-based diagram of one
session's turns and the agents they spawned — the same underlying data,
laid out as a graph instead of a chronological feed. Flow always draws
exactly one session ("All sessions" resolves to the most recently active one
in the current workspace filter); tag chips and the search box only affect
the list view; a small toolbar (Fit / Zoom in / Zoom out, a color legend,
and a status line) sits above the canvas, which supports drag-to-pan and
scroll-to-zoom.

- **Turn nodes** are laid out by `parent_uuid`/`last_uuid` lineage (see Turn
  lineage, above) rather than by simple `turn_id`/timestamp order — a
  parent's column continues straight through its main child, and only a
  later sibling takes a new column — but the column itself reads
  **newest-at-top**: the lineage walk numbers its nodes oldest-first, and
  final row placement reverses that walk before assigning any node a
  position, the same reverse-chronological convention the tool-call and
  agent-call stacks below are drawn in (see Lane two, Lane three). A turn's
  node therefore sits *above* the parent it continued from, not below it. A
  **fork** — two turns continuing the same parent — draws as two separate
  branches side by side instead of one node overwriting the other. Each box
  is colored by tag
  (plan/build/fix/validate/docs/ops/chat/untagged/system, matching the list
  view's colors) and shows its full title, timestamp, tool/agent counts,
  duration, and a warning badge for a failed tool call or a non-`complete`
  status. The title is never truncated: it's greedily word-wrapped to the
  node's width (long unbroken tokens — a path, an id — are hard-split rather
  than left to overflow the box) and the node grows taller to fit however
  many lines that takes, up to a safety cap of 8 lines, past which the last
  line does end in an ellipsis but the full text stays one click away in the
  tooltip and the modal. A turn bearing `task_id` (the `system:task-result`
  turn a background task's completion notification produced — see Background
  tasks, above) gets a "task ▶" marker in its subtitle. Where the open
  database has no lineage columns yet (or none of this session's turns could
  be matched by them), Flow falls back to one straight chronological chain
  and says so in its status line. Every turn column is really three lanes
  deep, one node type per lane, worked outward from the turn:
- **Lane two: the turn's own tool calls, and its agents.** Unlike the list
  view's collapsed-by-name summary, Flow draws **one node per call**,
  stacked **newest-first** — the same reverse-chronological convention the
  turn spine itself now reads by (see Turn nodes, above), so a call stack
  reads top-to-bottom the way the column above it does — tinted by the
  call's own `tag` — the same plan/build/fix/validate/docs/ops/chat colors a
  turn node uses, one lane in from it (a database that predates
  `tool_calls.tag` just draws an untinted node, same as before) — and
  labelled by the logger's own `summary` when the row has one, falling back
  to the tool name plus a short hint pulled straight from its input (a
  file's basename, a URL's host, a command, the head of a prompt) for a row
  that predates the column — enough to tell two `Read`s apart without
  opening either. A call that errored is colored accordingly regardless of
  its tag tint; a call that spawned a background task gets a small "▶"
  marker and its own dashed edge (see Background-task edges, below). A stack
  longer than 120 calls keeps its **newest** 120 and collapses the **older**
  tail into one "+N more" node rather than growing the canvas without bound
  (a shown call's own "call *k* of *n*" label, in its per-call modal below,
  still counts chronologically regardless of which end got capped, so it
  means the same thing it does in the collapsed list view); opening the "+N
  more" node opens the owning turn's modal instead of a call's, since that's
  where the rest of the trace already lives. Any agents the turn spawned sit
  in this same lane, below its call stack: agents from the same workflow run
  are drawn inside a shared labelled group box (the `workflow_id`) with
  their own sequential connectors, exactly mirroring how the list view's
  detail panel groups them; a directly-spawned (`Task`) agent with no
  `workflow_id` gets its own ungrouped node instead. **A classified agent's
  node is tinted by its own `tag`, exactly like a turn's** — the same seven
  colors, so an agent that did `fix` work reads as a `fix` node at a glance
  next to `fix`-tagged turns; an unclassified agent (an older database, or
  one still waiting on its Haiku call) keeps the plain accent-colored box it
  has always had, matching the legend's "sub-agent" swatch. Like a turn
  node, an agent node's own label is never truncated: it's greedily
  word-wrapped to the box width (long tokens hard-split, exactly as a turn
  title is), and the box grows to fit — a full written title gets the same
  generous 8-line budget a turn's title does, while a plain, unclassified
  `agent_type`/description label keeps a tighter 3-line one. The
  per-character-class width budget every wrapped label (and every call's
  tool name and summary line, in every lane) is measured against is derived
  from that font class's own actual em-width — mono, sans, size and weight
  all measured rather than guessed at a single estimate — which is what
  fixed the widest agent names and call summaries running out of their box
  before the per-class figures were tuned.
- **Lane three: each agent's own per-call nodes.** Where the database has
  `agent_tool_calls` rows for an agent (see Subagents / `agent_tool_calls`,
  above), that agent's calls are drawn the identical way — one node per call,
  not per tool name, newest-first exactly like the turn's own stack, with the
  same tag tint, summary-or-hint labelling, error coloring, and the same
  "+N more" cap (again keeping the newest calls and collapsing the older
  tail) — one lane further right, connected by an edge from *that agent's*
  node rather than from the turn. This is what makes a sub-agent's own flow
  visible on the canvas instead of only inside its modal: a workflow agent
  that ran five tools shows five small, tag-colored boxes hanging off it in
  reverse order of when it ran them, not just a tool-call-count number. An
  agent with no `agent_tool_calls` rows yet (not backfilled — see Backfill
  trigger, above) simply has no lane-three nodes, same as it has none in an
  older database without the table at all.
- **Background-task edges.** A lane-two or lane-three call node carrying a
  `task_id` gets a curved dashed edge to the turn node whose own `task_id`
  matches it — visually connecting "this call kicked off a background task"
  to "this turn is what reported it done", even though the two can be far
  apart in the layout. A call carrying a `run_ref` additionally draws a
  second dashed edge to whichever workflow group box or agent node that run
  or agent id resolves to. Either edge is simply omitted when its target
  wasn't rendered (an older, un-backfilled database, or the matching turn
  fell outside a capped session) — nothing errors, the graph just has one
  fewer edge. The legend's dashed "▶ background task" swatch covers both.
- **Every edge is obstacle-avoiding, and none is ever drawn through a
  node.** An edge is first tried as the direct curve Flow has always drawn,
  sampled along its length against every drawn box (each inflated by a small
  clearance collar) through a uniform bucket grid over the canvas, so the
  check stays cheap regardless of how large the graph gets — a short edge,
  which is most of them, passes this test and is drawn exactly as before. An
  edge that would cut through a box instead gets re-routed **orthogonally**,
  through the gutters the layout already leaves open — the page margins, the
  gap between two turn columns, the two lane gaps, and the gap between rows
  — by a small **Dijkstra search** over just the handful of channel x's and
  band y's nearest that edge's own endpoints: bounded work per edge no
  matter how big the session gets, corners priced so a route prefers fewer
  bends over a shorter but zig-zagging one, and edges sharing one channel
  spread across parallel tracks so they read as distinct lines instead of
  overlapping. Every routed segment is re-checked against every obstacle
  once the full path is built, so nothing is ever drawn that hasn't been
  proven clean first — this is the graph's **zero-crossing guarantee**: an
  edge never overlaps a node it isn't one of the two endpoints of. On the
  rare edge neither the direct curve nor the router can thread cleanly (a
  layout with no gutter wide enough to route through), Flow falls back to
  the plain curve or a straight line, faded and dashed under an `unclean`
  CSS class — visibly not-quite-right rather than silently wrong, and never
  a crash. Every edge's path is computed once per render, never again on
  zoom, scroll, or hover.
- **Every edge points where it flows.** A single arrowhead marker, shared by
  the whole graph, sits at the *destination* end of every connector except
  the short inner stack links, so the direction of flow reads straight off
  the picture: parent turn → child turn, turn → the calls and agents it
  made, agent → its own calls, and a spawning call → the turn that reported
  a background task finished. The marker takes its color from whichever
  edge references it (`fill: context-stroke`, with a plain neutral fallback
  for a browser without that CSS feature, detected once at load rather than
  per edge) so a tag-tinted, faded, or `unclean` edge's head always matches
  its own line with nothing to recolor by hand, and it's sized and
  positioned so its tip lands exactly on the border of the node the edge
  terminates at, never overlapping the box itself.
- **Click any node — turn, call, agent, or agent call — to open a modal**
  with that node's full detail: the same content the list view's expanded
  row or Agents section would show for a turn or agent (full prompt, full
  response, or an agent's prompt/result), and for a call node its own
  **per-call modal** — labelled "call *k* of *n*" so its position in the
  stack is never lost — showing that one call's input, result, truncation
  flags, and (when set) its `task_id`/`run_ref`, fetched lazily by primary
  key only once the node is clicked rather than loaded up front for layout.
  This is the same detail the collapsed list view's tool-call trace shows;
  Flow just gets to one call directly instead of via the owning turn's or
  agent's full list. The node itself is keyboard-reachable too (`Tab` then
  `Enter`/`Space` opens the same modal); `Escape` or the backdrop closes it,
  and nested modals (open a turn, then a call inside it) stack and unwind
  independently.
- Very large sessions are capped (600 turns) to keep the graph responsive;
  a capped session says so in the status line rather than silently dropping
  turns without explanation.

**Files touched**: derived on the fly from a turn's own `tool_calls`, not a
stored column — any database that has `tool_calls.input_json` can answer
"what did this turn write?". A turn's detail panel gets a **Files touched**
section listing every distinct path named by its `Write`/`Edit`/
`NotebookEdit`/`MultiEdit` calls, each with which tool(s) touched it and a
`×N` count when the same file was written more than once in that turn. In
standalone mode a path is plain text — a `file://` page has nothing to open
it with. In service mode, each path is a real link to `/view?path=<path>`
(so middle-click, `Cmd`/`Ctrl`-click, and "open in new tab" all still work),
but a plain click is intercepted and opens the file in a **modal** instead —
`fileview.html` loaded into an inline iframe, with an "open in tab ↗" link in
the modal header for anyone who wants the full page after all — so previewing
a touched file never loses the audit page's own scroll position or filters
the way navigating away to a new tab would have. See Service mode, next.

### Dashboard view

The third option in the `List / Flow / Dashboard` toggle turns the same rows
into a set of aggregate sections — what the whole audit log adds up to,
priced by the identical `estCost()` every list-view and Flow tooltip uses
(see Pricing, above), so the Dashboard's totals are the same per-row figures
summed, never a second calculation that could drift from them. It is scoped
exactly like the list view — the workspace filter, the Hide-system-turns
toggle, and the session selector ("All sessions" is the default and gives
the whole-database aggregate) all narrow it the same way they narrow the
turn list. Every figure comes from a SQL `GROUP BY` (by model, so pricing
only ever has to multiply over the handful of distinct models actually seen,
never loop the whole `turns` table in JS), and every chart is drawn from a
table the page builds regardless, so a page that can't reach the Chart.js CDN
falls back to showing that table in place of the picture, with identical
numbers underneath. A **pricing bar** across the top of the view (provider
selector, the Vertex endpoint choice, a "Rates, sources & notes…" button) is
the same control described under Pricing, above; changing it re-renders
every section here — and, if you happen to be looking at Flow or the list
instead when it changes, those too, since cost figures appear in all three
views.

Before any total is read, an unpriced-model warning chip appears if the
current range contains one (see the unpriced-model rule under Pricing,
above). The sections, top to bottom:

1. **Headline** — tiles for est. total cost, total tokens (turns *and*
   sub-agents combined, which is why this figure is larger than the plain
   turn-token count the page-top totals bar shows), turns, sessions,
   workspaces, agents (with their tool-call count), tool calls (with errors,
   and how many more were made by sub-agents), the date range covered, and
   **Cache savings**: what the tokens actually read from the prompt cache
   would have cost as fresh input, minus what they cost at the cache-read
   rate instead — `cache_read_tokens ÷ 1,000,000 × (input rate − cache-read
   rate)`, summed across turns and agents together.
2. **Activity & cost over time** — a stacked daily bar (input / output /
   cache-read / cache-write tokens) with an overlaid est.-cost line; days
   with no activity are drawn as gaps rather than skipped (capped at 400
   days), so the axis reads as a real calendar rather than a compressed one.
3. **By workspace** — sessions, turns, agents, tokens and est. cost per
   workspace, sorted by cost, as a bar chart or a table.
4. **By tag** — turns, tokens and cost per tag, as a doughnut (share of
   turns) or a stacked-tokens-plus-cost-line bar; a sub-agent is counted
   under its *own* tag here, not its parent turn's (see Subagents /
   Classification, above).
5. **Most expensive turns** — the top 10 turns by estimated cost. Cost can't
   be ordered in SQL without the rate table, so a proxy expression ranks the
   400 likeliest candidates in SQL at the most expensive rates in the active
   table, and the real top 10 is picked out of that candidate set in JS.
   Clicking a row opens the same detail panel the list view would for that
   turn. A **Turn durations** histogram (by wall-clock bucket) sits
   underneath it.
6. **Sub-agents** — tiles for **Delegation share** (`agents' output tokens ÷
   (turns' output tokens + agents' output tokens) × 100`: how much of the
   writing across the range was done by sub-agents rather than the main
   loop), est. sub-agent cost (and its share of the overall total), and
   average tool calls per agent; then a breakdown by agent type, and, when
   any exist, a breakdown by workflow run.
7. **Efficiency** — plain-language ratios computed entirely from numbers the
   sections above already gathered, nothing newly queried:
   - **Cache hit ratio** — `cache_read_tokens ÷ (input_tokens +
     cache_read_tokens + cache_creation_tokens) × 100`: the share of the
     whole input side of the conversation that was served from the prompt
     cache instead of sent fresh. Higher is cheaper.
   - **Thinking share of output** — `thinking_tokens ÷ output_tokens × 100`:
     how much of what the model wrote was reasoning it never showed. Since
     thinking tokens are billed as output and are already counted inside
     `output_tokens` in this schema (see Schema, above), this is a share of
     that existing total, never an amount added on top of it.
   - **Avg tool calls / turn** — total tool calls over total turns in range.
   - **Avg sub-agents / turn** — total agents over total turns in range.
   - **Est. cost / turn** — the whole priced total (main loop and sub-agents
     together) divided by the turn count, followed by the same cost-per-turn
     and avg-tokens-per-turn breakdown by tag underneath.

A database missing something a section needs — no `sessions` table, no
`agents` table, no `tool_calls` table, or no timestamps at all on `turns` —
doesn't error: that section reports plainly why it has nothing to show, and
every such gap is also collected into an "About this database" note block at
the bottom of the page, the same one place a reader would look to understand
why a section is empty.

### Service mode

Loading the viewer through `service.py` changes three things, all handled by
one `probeService()` call on page load (a 1s `/api/health` request that's
silently ignored — falling back to ordinary standalone mode — if nothing
answers, or the page wasn't itself loaded over `http(s)`):

- **Auto-load, no file picking.** The "Open database…" button, the "Reload
  file" button and the empty-state file-picker screen are all hidden — there
  is nothing to pick. The page fetches `/api/db` on load and renders it
  exactly as it would a dropped file, using the response body as the source
  ArrayBuffer.
- **A "live" badge** appears next to the title (green dot, the port after
  it) once the initial load succeeds, meaning "this page updates itself."
  The page also opens `/api/events` and reloads from `/api/db` (debounced by
  500ms, so a burst of writes for one turn collapses into a single reload)
  every time a `db-change` event arrives — so a turn logged by the `Stop`
  hook in another terminal shows up here without a manual refresh. Anything
  the user had set up by hand — scroll position, how far the list was paged,
  the Flow view's pan/zoom — is captured before a live reload and restored
  after it; the current filters live in shared state and just carry over. If
  the connection drops (the service restarting, a network hiccup) the badge
  turns red ("stale") rather than erroring the page — you keep looking at
  the last snapshot until the connection, which `EventSource` reconnects on
  its own, comes back.
- **Files touched links resolve.** Since there's now a service to ask, each
  path in a turn's Files touched panel becomes a real link (see above) to
  `/view?path=<path>` — a click previews it in a modal, and the link still
  behaves like an ordinary link (new tab via middle-click, `Cmd`/`Ctrl`-click,
  or the modal's own "open in tab ↗").

### Merge database UI

A **Merge database…** button appears next to the live badge, service mode
only — there's nobody to upload to from a `file://` page, so the control
stays hidden there (`enterServiceMode` is what un-hides it). Clicking it
opens a modal (`openMergeModal`) that:

- takes a file by its own file picker or by drag-and-drop onto a drop zone —
  the page-wide drop handler that a dropped `.db` normally triggers in
  standalone mode is inert in service mode, so this drop zone owns the
  gesture outright, with no risk of the two handlers fighting over the same
  file;
- refuses a file over **512 MiB** (the same cap the service itself enforces)
  before ever uploading it, and separately sniffs the first bytes of the
  file for the SQLite magic header, client-side, so "that's not an audit
  database" or "that file's too big" is an instant, readable message instead
  of a round trip to the service followed by a generic error;
- uploads the chosen file's raw bytes to `POST /api/merge` as
  `application/octet-stream`, with a 15-minute timeout generous enough for a
  genuinely large backup, and shows a busy state ("Uploading … and
  merging…") for the whole round trip, with the button disabled so a second
  click can't fire a second upload mid-merge;
- renders the response as a table, one row per table
  (sessions/turns/tool_calls/agents/agent_tool_calls/cursors) with columns
  **imported / replaced / skipped (duplicate)** — built by folding whichever
  shape of counters the service actually returned (flat `<table>_<verb>`
  keys, or nested `{table: {imported, ...}}` objects) onto that one fixed
  layout; a counter this mapping doesn't recognize is listed underneath
  instead of silently dropped, so a counter the engine starts reporting
  later is never lost, just not yet columnized;
- states the merge engine's own **dedup semantics** once, under the table,
  in plain language: rows are matched on their own identifiers
  (`prompt_uuid`, `session_id`, `(session_id, agent_id)` — see How rows are
  matched, under Merge (corporate restore), above), so re-uploading the same
  backup a second time reports everything skipped rather than duplicating
  anything;
- surfaces the service's own words on failure — a JSON `{error}` shown
  verbatim, a plain-language reason for a `404`/`501` (an older service with
  no `/api/merge` at all) or a `413` (rejected as too large), or the
  stripped text of a generic HTTP error page — never a raw stack trace; and
- schedules the same debounced reload a live `db-change` event would (see
  Service mode, above) once the merge succeeds, as the belt to that event's
  own braces, since the merge's own commit already fires one.

Every byte of the upload, the validation, and the merge itself happen inside
the `service.py` already running on this machine — nothing about the file's
contents leaves it.

### `/view` — the artifact renderer (`fileview.html`)

`/view?path=<absolute path>` never reads the filesystem itself — every byte
comes from `service.py`'s own `/api/file`, so the same workspace-root
allowlist and 403 behaviour apply here as everywhere else (see Security,
above). It picks a renderer purely by the path's extension:

- **`.html`/`.htm`/`.xhtml`** — the page actually **runs**, live, inside a
  sandboxed iframe (`sandbox="allow-scripts"`) whose `src` is `/api/file?…`,
  not `srcdoc` — so any relative fetch the page makes resolves against
  `/api/` and fails closed rather than reaching somewhere unexpected, and the
  sandbox keeps it in an opaque origin that can't reach back into `/api/db`.
- **`.md`/`.markdown`/`.mdown`/`.mkd`** — rendered with `marked`, then run
  through `DOMPurify.sanitize` before it ever touches the DOM; links inside
  the rendered document open in a new tab with `rel="noopener noreferrer
  nofollow"`. A **Rendered / Source** toggle switches to the raw text (which
  falls back to the syntax-highlighted view below if `marked`/`DOMPurify`
  failed to load — raw HTML is never dumped into the page unsanitized).
- **Everything else** — `highlight.js`, language guessed from the extension
  (falling back to `highlightAuto` when it isn't recognised), with a
  line-number gutter. A binary file (sniffed by a `\x00` byte, or an
  unfamiliar extension that doesn't decode as UTF-8) shows a notice with size
  and content type instead of dumping bytes into the DOM, and a **Raw** link
  to download it via `/api/file` directly.
- Images (by extension or a `image/*` content type) render directly in an
  `<img>`.

A `HEAD` request runs first, so the page can show size/last-modified/content
type — and detect a 403/404 — without pulling a large file into memory just
to find out. Every untrusted string (the path, an error message, file text
shown as source) is written with `textContent`; the only two exceptions are
the DOMPurify-sanitized markdown container and the sandboxed iframe, both
deliberate and isolated.

## Caveats

- **`Stop` doesn't fire on Ctrl+C.** If a session is killed mid-turn, that
  turn never gets a `Stop` sweep. It's still captured: `SessionEnd` (or the
  next session's `Stop`, since sweeps are idempotent and cursor-based) will
  eventually pick it up and finalize it — such turns end up with
  `status = 'swept'` instead of `'complete'`. If even `SessionEnd` never ran
  (the process was killed harder than Ctrl+C, or the hooks weren't installed
  yet at all), `sync` is the catch-all: run it (or `/audit-sync`, or
  `sync --workspace` for just one project) and it backfills anything still
  missing straight from the transcript files on disk, no matter how long ago
  they were written.
- **The transcript format is internal to Claude Code and undocumented.** It
  may change without notice; `read_new_records` silently skips lines it
  can't parse as JSON rather than raising, and turn assembly is intentionally
  defensive against missing/reordered fields.
- **Subagent (sidechain) traffic is excluded from `turns`.** Lines with
  `isSidechain` never join the main conversation's turns; each subagent is
  summarised as one row in `agents` instead, joined to its parent turn.
- **The service isn't running until something starts it.** The watchdog only
  spawns it from inside a `Stop`/`SessionEnd` hook, so on a fresh install (or
  right after a reboot, without `install-startup`) nothing is listening on
  `http://127.0.0.1:4737/` yet — that's a plain connection-refused, not a bug
  — until either a Claude Code turn finishes, you run `service.py start` by
  hand, or you set up `install-startup` (see The service, above) so it's
  already up before either.
- **Claude Code auto-cleans transcripts after ~30 days.** That's the whole
  reason this exists. As a second line of defense beyond the SQLite mirror,
  `SessionEnd` also copies the raw transcript verbatim to
  `<audit dir>/transcripts/<workspace-folder>-<session_id>.jsonl` (`<audit
  dir>` is `~/.claude/audit` by default — see What it does, above), and the
  whole subagent tree to the matching `-subagents/` directory, before they
  can age out.

## Future / org rollout

A per-user plugin install only covers sessions run under that account. To
roll out more broadly:

- **Team install via git**: push this repo to your git host; each developer
  runs `claude plugin marketplace add <repo>` + `claude plugin install
  claude-audit@claude-code-tools`. Version bumps in `plugin.json` propagate
  as plugin updates.
- **Project-level enablement**: enable the plugin in a project's own
  `.claude/settings.json` (`enabledPlugins`), checked into the repo, so every
  contributor gets audit logging in that workspace.
- **Managed settings** (org-enforced, non-overridable `settings.json`
  deployed by IT/security) to guarantee the hooks run for every user on
  every machine, not just where someone opted in.
- **OTel export** as a complementary, centralized channel — Claude Code's
  built-in OpenTelemetry support (`OTEL_LOG_USER_PROMPTS` and related env
  vars) can stream prompt/usage telemetry to a central collector, which
  would cover cross-machine visibility that a local SQLite file — even the
  machine-wide one this plugin now defaults to — can't.
- **Machine reimages / rebuilds**: back up `~/.claude/audit/audit.db`
  (checkpointed — see Merge, above) like any other data directory, and use
  `audit_log.py merge --from BACKUP.db` to fold it back into a rebuilt
  machine's fresh database without losing anything logged since the rebuild.
